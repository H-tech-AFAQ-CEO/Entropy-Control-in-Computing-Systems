01Framing: entropy as a cost model

Three runtime costs track uncertainty, and each has a formal bound.

  • Branch prediction. Chen, Coffey and Mudge (1996) showed that a predictor is a compressor of the branch-outcome stream, so its misprediction rate cannot fall below the conditional entropy of the next outcome given history. For independent outcomes with taken-probability p, no predictor beats min(p, 1−p).
  • Caches. Miss rate depends on how concentrated the address distribution is. Locality is low entropy in that distribution (working-set model, Denning 1968).
  • State space. The number of reachable states, log₂|S| bits, bounds what a test suite or a reviewer must cover.
H(Xt | X<t) = − Σ p(x, h) · log₂ p(x | h)Conditional entropy of the next event given history: the floor for any predictor of that stream

Entropy is never removed for free. Ordering, indexing and compression convert it into one-time or amortized work, which section 04 prices.

03Worked examples

Small, runnable, and tied to a number.

A · Shrink the state space with a sum type

Three flags encode 2³ = 8 states, but only 4 are meaningful (idle, loading, error, ok). The sum type encodes exactly those 4, removing log₂(8/4) = 1 bit, and makes the other 4 unrepresentable instead of untested.

// Before: 8 representable states, 4 meaningful
type Bad<T> = { loading: boolean; error?: Error; data?: T };

// After: exactly 4 states
type Fetch<T> =
  | { tag: "idle" }
  | { tag: "loading" }
  | { tag: "error"; err: Error }
  | { tag: "ok"; data: T };

function render<T>(s: Fetch<T>): string {
  switch (s.tag) {
    case "idle":    return "";
    case "loading": return "…";
    case "error":   return s.err.message;
    case "ok":      return String(s.data);
    default: { const _exhaustive: never = s; return _exhaustive; }
  }
}

Adding a fifth variant without handling it becomes a compile error through the never check. Sources: Harel (statecharts) and the "make illegal states unrepresentable" idiom from the ML tradition.

B · Branch entropy, measured

The same loop does identical arithmetic on identical values. Only the order of the data changes, so only the entropy of the branch-outcome stream changes.

long branchy(const int *a) {            // data-dependent branch
    long s = 0;
    for (unsigned i = 0; i < N; i++)
        if (a[i] >= 128) s += a[i];
    return s;
}
long branchless(const int *a) {         // no data-dependent branch
    long s = 0;
    for (unsigned i = 0; i < N; i++)
        s += a[i] & -(a[i] >= 128);
    return s;
}

Three readings. Predictable beats unpredictable by roughly 6–8× on the branchy loop. Branchless removes the penalty at a fixed cost, about 3.2–3.4 ms here. And once the branch is predictable, the branchy version is as fast or faster, so branchless is insurance against disorder, not a free win.

Compiler caveat. With default flags at -O1, gcc already converted the branch to a conditional move: random and sorted measured 4.1 and 3.8 ms, almost no gap. The table above used -fno-if-conversion -fno-if-conversion2 to expose the effect. Check what your compiler emitted before concluding a branch is costing you.

Environment: 2 vCPU Intel Xeon @ 2.10 GHz virtual machine, gcc 13.3.0. Absolute numbers will differ on your hardware; the ratio is the finding. Single-environment results on a shared VM carry noise.

C · A binary search with no data-dependent branch

Each step halves the interval and yields about one bit, the information-theoretic maximum for a comparison. The conditional move removes branch misprediction from the loop.

// First index with a[i] >= x, or n if none. Requires n >= 1, sorted input.
size_t lower_bound_bl(const int *a, size_t n, int x) {
    const int *base = a;
    while (n > 1) {
        size_t half = n / 2;
        base = (base[half - 1] < x) ? base + half : base;  // cmov
        n -= half;
    }
    return (size_t)(base - a) + (*base < x);
}

Checked against a reference implementation on every array length from 1 to 200, with duplicates, at every probe value in and around range: 20,858 test cases, 0 mismatches.

04Limits: when ordering costs more than it removes

Ordering is work. Below are the points where that work stops paying.

Sorting lower bound

Any comparison sort needs at least log₂(n!) ≈ n log₂ n − 1.44 n comparisons on worst-case input. You beat it only by exploiting structure already present. That is the field of adaptive sorting (Mannila 1985; Estivill-Castro and Wood 1992), and it is why Timsort is fast on nearly sorted data.

Amortization break-even

A linear scan costs n per query. Sort-then-search costs n log n + q log n. Sorting wins when q > n log n / (n − log n), which is about log n queries. For a handful of lookups, do not build the index.

Maintenance cost

Order must be kept, not just built. The RUM conjecture (Athanassoulis et al. 2016) argues that an access method cannot minimize read, update and memory overhead at once. Log-structured merge trees buy write throughput by tolerating disorder at read time. Dynamic lower bounds from the cell-probe model (Fredman and Saks 1989; Pătrașcu and Demaine 2006) formalize why maintaining order under updates has a price.

Incompressibility

Data with high Kolmogorov complexity cannot be cheaply ordered or compressed. Kolmogorov complexity is uncomputable, so "the best possible structure" can never be certified in general (Li and Vitányi).

Thermodynamic floor

Landauer (1961): erasing one bit dissipates at least kT ln 2, which is 2.87 × 10⁻²¹ J at 300 K. The bound has been verified experimentally (Bérut et al., Nature 2012). Bennett (1973) showed computation can be made logically reversible, avoiding erasure at a cost in space or time. Real hardware dissipates orders of magnitude above this floor, so in practice your limit is data movement, not bit erasure.

Takeaway. Order data when queries per update comfortably exceed log n, when the data arrives already structured, or when the payoff is a predictable branch or cache stream. Do not order data that is read once, changes constantly, or is already close to incompressible.

05Design rules

Six rules you can apply in a review.

  1. Encode only valid states.Prefer sum types and explicit state machines to sets of flags. Count representable versus meaningful states; the gap is wasted bits and untested cases.
  2. Index or sort only past the break-even.Expect more than about log n queries per update, or a read-heavy workload, before paying to maintain order.
  3. Make address and branch streams predictable.Struct-of-arrays, sorted batches, and branchless inner loops where data order is outside your control.
  4. Prefer proven bounds over hand-tuned constants.Use cache-oblivious or I/O-optimal structures rather than hard-coding cache sizes that change with the next CPU.
  5. Compress when bandwidth is the bottleneck.If the CPU is the bottleneck, decode cost can erase the saving. Measure both.
  6. Measure before and after.Use perf stat -e branch-misses,cache-misses. Theory gives the direction and the bound; your hardware supplies the constant. Check the compiler's output first.

Review checklist

  • Which states can this type represent that the system never enters?
  • What does the branch-outcome stream look like on production data, not test data?
  • How many reads happen per write? Is it above log n?
  • What is the bottleneck: CPU, memory bandwidth, or the network?
  • Did the compiler already make this change for us?

06Reproduce the benchmark

The full program is below so the numbers in section 03 can be checked on your own machine.

// bench.c  ·  gcc -O1 -fno-if-conversion -fno-if-conversion2 -o bench bench.c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#define N (1u << 22)
#define REPS 100

static int cmp(const void *a, const void *b) { return *(const int *)a - *(const int *)b; }
static double now(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec * 1e-9; }

__attribute__((noinline)) long branchy(const int *a) {
    long s = 0;
    for (unsigned i = 0; i < N; i++) if (a[i] >= 128) s += a[i];
    return s;
}
__attribute__((noinline)) long branchless(const int *a) {
    long s = 0;
    for (unsigned i = 0; i < N; i++) s += a[i] & -(a[i] >= 128);
    return s;
}
static double run(long (*f)(const int *), const int *a, long *out) {
    double t0 = now(); long s = 0;
    for (int r = 0; r < REPS; r++) s += f(a);
    *out = s; return (now() - t0) / REPS * 1e3;   // ms per pass
}
int main(void) {
    int *a = malloc(N * sizeof *a); srand(42);
    for (unsigned i = 0; i < N; i++) a[i] = rand() % 256;
    long s1, s2, s3, s4;
    double t1 = run(branchy, a, &s1), t2 = run(branchless, a, &s2);
    qsort(a, N, sizeof *a, cmp);
    double t3 = run(branchy, a, &s3), t4 = run(branchless, a, &s4);
    printf("checksums equal: %s\n", (s1 == s3 && s2 == s4 && s1 == s2) ? "yes" : "NO");
    printf("random,  branchy   : %7.3f ms/pass\n", t1);
    printf("random,  branchless: %7.3f ms/pass\n", t2);
    printf("sorted,  branchy   : %7.3f ms/pass\n", t3);
    printf("sorted,  branchless: %7.3f ms/pass\n", t4);
    free(a); return 0;
}
